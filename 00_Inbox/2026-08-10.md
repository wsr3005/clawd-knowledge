# AI / Agent 战略情报｜2026-08-10

**一句话结论：** Agent 基础设施正在同时跨过三个门槛：Claude Code 开始原生协调独立会话并调整权限默认值，Cloudflare 提供轻量隔离浏览器，而最新研究把 Harness 的状态调用从手工规则推进到可训练策略；当前应小步验证，不要盲目重构。

## 1. Claude Code：独立会话可互发摘要，Auto Mode 将成为部分订阅默认权限模式

【事实】**已证实。** Anthropic 官方 ClaudeDevs 宣布：Claude Code 的独立会话现在可以互发消息；发送的是摘要，而不是完整历史或文件，接收会话可在任务中途接收，Claude 也可主动联系另一会话。该功能目前支持 macOS、Linux。官方同时宣布，自 8 月 14 日起，Auto Mode 将成为 Pro、Max、Team 用户的默认权限模式；Shell 命令和动作会交由独立分类器审查。官方 X 帖称测试中该模式识别了 89% 的危险命令，而人工审批识别 14%。

【影响】这直接命中昱桥当前多 Session / 多 Agent 的上下文同步和长任务频繁停顿问题。跨会话摘要可减少共享 Markdown 的人工搬运；但 Auto Mode 是权限边界变化，不能把“默认更自动”误读为“生产环境可无人复核”。

【动作】更新 Claude Code 后，把两个独立终端间的交接优先改为跨会话摘要；8 月 14 日后检查默认权限是否变化。普通仓库任务可试 Auto Mode，发布、生产基础设施、凭证和不可逆操作仍保留人工确认与 Git/沙箱隔离。

【证据】[Anthropic 官方：跨会话消息](https://x.com/ClaudeDevs/status/2085817074816070014)；[Claude Code 官方文档：Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging)；[Anthropic 官方：Auto Mode 默认值公告](https://x.com/ClaudeDevs/status/2085794862608318627)；[AI HOT 聚合入口（4 个独立信源）](https://aihot.virxact.com/items/cmsjaksyd04hlroo5hdy2qd4i)

【可信度/待核验点】功能与适用平台由官方来源确认；89%/14% 为 Anthropic 自报测试结果，未在本次核验中获得完整实验设计，不应外推为所有真实任务的安全率。

## 2. Cloudflare Kitesurf：面向 Agent 的无状态轻量浏览器已进入 Browser Run Beta

【事实】**已证实。** Cloudflare 发布 Kitesurf：它运行在 Workers 的 V8 isolates 上，面向 Agent 的临时、隔离、无状态浏览任务；Beta 期间免费，可经 Browser Run Quick Actions、CDP 以及 MCP 客户端接入。官方明确列出限制：暂不适合视频、WebGL、需要真实 TLS 指纹通过 Bot Challenge 的站点，以及依赖持久登录状态的长会话。Cloudflare 在 14 个 URL、每项 5 次运行的自测中报告其 CPU/内存低于 Chromium，但墙钟时间更慢。

【影响】它可能成为 Hermes/OpenClaw 广域抓取、HTML 提取和一次性截图的低成本执行层，尤其适合并发、突发任务；但不能替换处理登录态、强反爬和复杂媒体的 Chromium。真正价值不是“新浏览器”，而是 Agent 浏览资源成本与隔离粒度出现了新的基础设施选项。

【动作】把 Kitesurf 加入无登录采集任务的 A/B 候选，比较成功率、耗时、成本和页面兼容性；在结果稳定前不替换现有 Chromium 路径，并保留按站点自动回退。

【证据】[Cloudflare 官方发布](https://blog.cloudflare.com/kitesurf)；[Cloudflare Browser Run 官方文档](https://developers.cloudflare.com/browser-run/kitesurf)；[AI HOT 聚合入口（3 个独立信源）](https://aihot.virxact.com/items/cmsjbn0kl058nroo5kq0m0jws)

【可信度/待核验点】产品形态、接入方式与限制由官方文档确认；性能数据来自 Cloudflare 自测，样本仅 14 个 URL，需用昱桥自己的目标站点复验。

## 3. EvoHarness-RL：Harness 的状态管理策略开始从手工规则走向训练

【事实】**已证实为论文结果，尚非通用生产结论。** UIUC 与 Meta AI 的论文 EvoHarness-RL 将 Agent 外部状态抽象为 Belief、Progress、Experience（BPE），先以监督微调学习状态动作，再用成本感知 GRPO 学习何时读取、更新和归并外部状态。论文在 ALFWorld 上以 Qwen3-8B 实例化，报告 seen split 成功率 96.9%、unseen split 86.6%。

【影响】这支持一个重要判断：长任务的下一阶段，不只是继续堆 prompt、工具和更大记忆，而是优化“何时读写哪类状态”。这与 Hermes 的 memories、skills、任务进度和验证回路直接相关，但单一具身环境结果不足以证明现有 Harness 应立刻推倒重来。

【动作】不追逐论文分数、不重构主系统；先用 BPE 作为现有长任务的审计框架：区分当前事实、任务进度、跨任务经验，并记录每次状态读写的成本与收益。只有在真实软件/自动化任务中出现可重复提升，再考虑自动化状态策略。

【证据】[论文原文：EvoHarness-RL](https://arxiv.org/abs/2608.05446)；[研究线索](https://x.com/omarsar0/status/2086509069762981896)

【可信度/待核验点】方法与数字来自论文原文；目前是 arXiv v1、单一 ALFWorld 实例化，尚不能证明对编码、浏览或商业工作流同样有效。
