# 2026-08-03 AI / Agent 战略情报

**一句话结论：** Agent 竞争正在同时沿两条线加速：前沿模型用可机器验证成果抬高能力上限，低成本开放模型与分层编排则开始重写日常开发的成本结构；但今天最该升级的是验证体系，不是追着宣传换主力。

## 1. Astra 展示“长程推理 + 形式化验证”，但不能外推成通用 Agent 已解决

【事实】**已证实（发布方事实）**：OpenAI 于 8 月 1 日公布其下一代主要模型 Astra 的内部版本在数学与理论计算机科学中产出 10 项结果，并发布论文、推理讲解及对应 Lean 4 证书仓库。OpenAI 称找到这些成功解所消耗的 token，按 Sol API 价格折算约 2,000 美元；论文由人类配合同一模型整理，之后由模型形式化。**尚未独立坐实**：外界仍缺少完整方法、尝试过多少失败问题、总人力与总算力成本等信息，因此不能据此推断 Astra 已具备通用可靠性。

【影响】对昱桥最重要的不是“下一代模型更聪明”，而是高价值 Agent 交付的范式正在从自然语言自证，转向“生成结果 + 可执行/可机器检查证据”。这会直接影响 Hermes、Codex 自动化、数据管道和商业内容生产的验收设计。

【动作】立即把原则定死：复杂自动化任务必须随产物交付可复跑的测试、截图差异、schema 校验、来源证据或其他机器可检查凭证；Astra 在公开可用、价格和真实 Agent 表现明确前，不据此调整当前主力模型。

【证据】[OpenAI 原始发布](https://openai.com/index/ten-advances-in-mathematics/)；[论文](https://cdn.openai.com/pdf/ten-proofs-oai.pdf)；[Lean 证书仓库](https://github.com/openai/ten-proofs)；[Gary Marcus 的方法学质疑](https://garymarcus.substack.com/p/openais-amazing-but-vastly-oversold)；[AI HOT 聚合入口（14 个独立信源）](https://aihot.virxact.com/items/cmsa77lmk02tcrox0gfhj3rcq)

【可信度/待核验点】发布材料与代码仓库均可访问，发布方事实可信度高；数学结论的学界复核、失败样本、全口径成本和跨领域泛化能力仍待核验。

## 2. DeepSeek V4 Flash 0731 把“开放低成本 worker”推到可认真评测的位置

【事实】**已证实**：DeepSeek 官方 Hugging Face 页面将 V4 Flash 0731 标为正式版本，取代 preview，权重采用 MIT License；支持 `low`、`high`、`max` 三档 reasoning effort，并给出面向 agent 场景的运行配置。官方自报其在多项 agent/coding benchmark 上明显优于旧 preview，并在部分项目超过 V4 Pro Preview。OpenRouter 当前列出的托管价为每百万 token 输入 0.09 美元、输出 0.18 美元，1M context；这是 OpenRouter 渠道价格，不等于所有平台统一价格。

【影响】它不必取代 Sol/Claude，但已经足以成为批量抓取、格式转换、初稿实现、低风险修复等 worker lane 的候选；如果质量过线，可把昂贵模型集中在架构、疑难任务和最终审查上。

【动作】将其列入隔离评测队列，而不是直接替换生产：用 3 类真实任务对比当前 worker——工具调用成功率、测试通过率、每个合格交付的总 token/成本；主审仍保留在更强且独立上下文的模型。Pi harness 的适配建议目前只来自 builder 实测，先作为试验入口，不当作官方兼容承诺。

【证据】[DeepSeek 官方模型页与权重](https://huggingface.co/deepseek-ai/DeepSeek-V4-Flash-0731)；[OpenRouter 模型与渠道价格页](https://openrouter.ai/deepseek/deepseek-v4-flash-0731)；[Elvis Saravia 的 Pi harness 实测建议](https://x.com/omarsar0/status/2084001897967444248)

【可信度/待核验点】发布状态、许可证、推理档位可由官方页面确认；benchmark 为厂商自报，Pi 兼容性为个人经验，尚需用昱桥自己的任务集复测。

## 3. `sol-advisor` 把分层模型调度做成 Codex 插件，但应借鉴架构、暂缓信任成品

【事实】**已证实**：开源项目 `sol-advisor` 将 Codex 工作流固定为 Sol High 负责任务拆解，Luna Max 做常规实现，Terra Max 做高风险实现，再由全新上下文的 Sol High 审查实际 diff 和验证证据；项目还要求核对 agent 角色、模型与 reasoning effort，并在无法确认路由时停止。仓库公开、MIT License，但目前仅 3 次提交，仍属非常早期。作者关于“不容易撞 weekly limit”的说法没有独立测量支撑。

【影响】真正有价值的是两个机制：按任务风险分层路由，以及用新上下文审查来隔离“同一对话里的共同幻觉”。这正好对应昱桥多 Agent/Kanban 流程里的成本与质量矛盾。

【动作】不直接安装进主环境；先吸收其协议：每个实现任务必须写清 objective、file ownership、interfaces、constraints、verification，最终审查读取实际 diff 与测试证据。若要试插件，只在 disposable repo 做安全审阅和端到端验证，确认不会改写本地 agent 配置后再决定。

【证据】[`sol-advisor` GitHub 原仓库](https://github.com/DannyMac180/sol-advisor)；[作者原始说明](https://x.com/daniel_mac8/status/2083607027813662810)

【可信度/待核验点】插件结构与保护机制可由仓库确认；节省额度、模型间质量等收益尚无独立基准，且项目成熟度低，不能直接视作生产级工具。
