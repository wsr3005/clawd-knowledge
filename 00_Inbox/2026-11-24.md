## 1. Claude Ship：能接手审查与修复，但 `/ship` 不是只读检查

【事实】已核验 Anthropic 发布的 Claude Ship：由 Code Review、处理审查反馈和失败检查的 PR Steward、按团队规则判断审批的 Claude Approvals 组成；后两者为测试版。仓库级服务面向 Team／Enterprise 的 GitHub 仓库，按 token 另行计费；观察模式中的审查和分类器调用也会计费。个人侧 `/ship` 按常规 Claude Code 用量计算。官方明确：该命令没有确认提示，可提交代码、推送分支并创建 PR，且可能包含未提交的新文件；禁止读取某文件的权限规则，不等于禁止将其提交。本机只读检查返回 Claude Code `2.1.330`，与官方列出的最低版本一致，但本次没有调用 `/ship`，未验证入口开放或端到端可用性。

【影响】投资驾驶舱、Openwrite 等工程的“写完之后还要追测试、追审查”新增了原生候选，不必先自建一套跟进机器人。但它跨过了昱桥要求明确授权的对外写入边界，不能把“帮我检查一下”解释成允许推送。自动审批也不等于独立人工验收，交易逻辑、凭证与数据迁移尤其不能因此放宽门槛。

【动作】已完成公告、计费、命令副作用及本机版本核对，未启用任何仓库服务、创建 PR 或运行付费任务。建议先保留现有本地审查；只有获准推送的独立测试仓库才试 `/ship`，执行前逐个核对待提交文件与敏感内容，不和主任务共用工作目录。若评估团队服务，先设支出上限、手动触发修复、审批只观察，并保留人工合并与 GitHub 分支保护；观察模式不是免费试用。

【证据】[官方发布与计费说明](https://claude.com/resources/articles/introducing-claude-ship)；[Claude Ship 官方文档](https://code.claude.com/docs/en/claude-ship)；[`/ship` 的确认、提交范围与本地执行规则](https://code.claude.com/docs/en/ship-command)；[Claude Approvals 的人工审查与分支规则边界](https://code.claude.com/docs/en/approvals)；[官方原始公告](https://x.com/ClaudeDevs/status/2124959436640858475)。本机证据：实际执行 `claude --version`。

【可信度/待核验点】发布内容、文档规则与本机版本：已核验。昱桥账号权限、命令入口、运行成本和修复质量：未实测。团队仓库服务与本地 `/ship` 是不同运行方式，不能把团队的后台运行能力套到本地命令；本地持续跟进需要会话保持打开、电脑保持唤醒。

## 2. GLM-5.4：新增视觉与周额度，但先别直接替换主模型

【事实】已核验 Z.ai 负责人原文：GLM-5.4 向全部 GLM Coding Plan 用户开放，新增视觉能力；对有周额度的用户，相比 GLM-5.3 增加 50% 额度。负责人另文提醒它倾向长时间思考，不适合简单的一行任务；性能提升属于厂商内部评测说法，本次未独立复现。当前官方接入文档与 FAQ 仍列 GLM-5.3，和新公告尚未同步；因此未采信中文转述中的完整配置与上下文规格。

【影响】它值得成为投资驾驶舱“看截图修界面”和工程测试任务的备用模型候选，工具仍可沿用现有 Claude Code，而不是再开一套 Agent。额度增加不等于每项任务更便宜：长思考可能抵消可用量收益，完成质量与等待时间必须一起看。官方 Coding Plan 限定支持的工具和场景，不能直接推定可作为 Hermes 任意后台任务的通用额度。

【动作】已合并重复发布线索，并核对负责人补充与套餐限制。建议仅在已有合适套餐、模型入口和计费归属确认后，用脱敏的截图修复任务与测试补全任务对照现有流程，记录测试通过情况、返工、耗时及真实额度消耗；没有现成权益就先观察，不为新闻购买。接入时隔离配置，不直接运行会改写全局 Claude 设置的安装脚本。本次未切换模型、改配置或消耗评测额度。

## 3. Claude 多账号有官方路径，但“全目录共享、不怕封号”不能照抄

【事实】官方认证文档明确支持用 `CLAUDE_CONFIG_DIR` 为工作和个人账号分别保存设置、会话历史及登录；但无 API key 的 Claude Console 登录存放在配置目录之外，不能靠该变量隔离。候选实践帖建议将 `settings.json`、`plugins`、`projects` 等软链接回主目录，并声称“不怕封号”。官方目录文档显示，`projects` 不只是可复用规则，还包含完整对话、工具输入输出与自动记忆；设置文件则可含权限、hooks 和环境变量。官方多账号支持不构成任何使用方式都免风控的保证。

【影响】对 Hermes／Kanban 调度与客户项目，真正要区分的是“复用技能”和“混用账号状态、历史及权限”。将这些目录重新指向同一处，会削弱原本的数据隔离；这是依据文件职责作出的风险判断，不是本机已经发生泄露的诊断。也不能反过来说合法的工作／个人双账号本身就违规。

【动作】已把社交帖的便捷配法与官方支持范围分开核验，不采用其“零封禁风险”结论。建议需要多账号时保留独立登录、会话和项目记忆，仅复用审查过且不含私密信息的规则／技能；不要整份共享含凭证或权限的设置，不部署自动轮换额度池。无需为多账号管理引入 T3 Code，继续使用现有工具栈。本次未新增账号、创建软链接或修改任何现有 profile。

【证据】[官方认证文档：多账号与 Console 例外](https://code.claude.com/docs/en/authentication#log-in-with-multiple-accounts)；[官方目录文档：会话记录、项目记忆与设置职责](https://code.claude.com/docs/en/claude-directory)；[原始实践帖，效果与安全保证待核实](https://x.com/gkxspace/status/2124840843165216801)；[B 级转述线索，非官方安全承诺](https://x.com/servasyy_ai/status/2124852965517430824)。

【可信度/待核验点】官方支持路径、例外及文件职责：已核验。社交帖关于 T3 Code 的实际兼容性、稳定性与封禁风险：待核实，本次未测试。上述风险来自共享本地状态的推断，不声称创建软链接就必然上传或泄露数据；这也不是今日新增的官方限制。
