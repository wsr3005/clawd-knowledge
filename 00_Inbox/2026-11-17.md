# AI / Agent 战略雷达｜2026-11-17

不换主栈：核对模型入口的账单与容灾，打戏 Skill 先卡商用授权；Codex 的恢复信号只够支持小步复测。

## 1. Hugging Face 改接 OpenRouter：接口没变，结算与故障边界变了

【事实】已核验 Hugging Face 官方公告：Inference Providers 的语言模型请求改经 OpenRouter 路由，失败时可尝试其他供应商；公告明确这些请求改由 Hugging Face 账号或组织结算，不再支持自带供应商 API key。仍可指定供应商或在设置中禁用供应商。图像、视频和音频生成不走这次新路由，图像、视频的自带密钥继续可用。需要保留一个核验断点：通用计费文档仍展示自带密钥方案，未清楚同步语言模型的例外；不能据此认定所有账号的旧配置已实测失效。

【影响】对小说模型评测、投资驾驶舱未来的模型入口，这是兼容性与成本边界变化，不只是“多一个模型商店”。原供应商余额、额度不能默认沿用到 HF 结算链路。工程推断：HF 与直接接 OpenRouter 共享部分上游依赖，不能再把二者视为完全独立的容灾通道。自动切换供应商也意味着敏感资料可能流向不同处理方，应限定允许的供应商。本次未审计项目配置，不声称现有生产链路已受影响。

【动作】已核验公告并交叉检查计费文档，记录两者的口径差异。建议在任何 HF 语言模型接入或恢复前，先确认实际扣款主体、预算上限和供应商允许名单；若依赖自带密钥或原供应商额度，先通过官方确认与受控小样验证，不直接迁移。需要独立容灾时，选择不共享该路由的合规直连渠道。本次未改接口、上传资料或调用付费推理。

【证据】[Hugging Face 官方公告与 Breaking change](https://huggingface.co/blog/openrouter)；[官方计费文档（仍保留通用自带密钥说明）](https://huggingface.co/docs/inference-providers/pricing)；[官方发布帖](https://x.com/huggingface/status/2122393775314264519)。

【可信度/待核验点】公告内容：高；具体账号生效状态、旧配置行为及账单归属：待核实。容灾相关性是根据路由变更作出的工程判断，不是本机故障测试。未采用厂商的性能提升数字，也不将本次变化外推到独立部署或下载模型。

## 2. h3-fight 打戏 Skill：代码 MIT，提示词库却是非商用许可

【事实】已回到作者仓库与许可文件核验：工具代码采用 MIT；提示词库、库对照页与演示 GIF 中作者有权授权的内容采用 CC BY-NC 4.0，明确限非商业目的复制、分享和改写。仓库提供提示词组织与检查方法，但不附可直接运行的 ComfyUI 工作流文件，需要自行搭建，模型与 LoRA 另有各自许可。README 将作者的出片测试环境列为改装 48GB RTX 4090，普通 24GB 显卡尚未验证；这不是我们的硬件实测。

【影响】它值得进入小说衍生视频的技术观察，但不能以“GitHub 显示 MIT”就把整套镜头库装进商业生产线。真正可借鉴的是“镜头组织—提交前检查—人工看片”的流程；许可、运行环境和成片质量是不同关卡。提示词库的非商用限制也不能机械解释成所有生成视频必然同样受限，输出权利仍需结合实际使用方式及模型条款核查。

【动作】已将个人源的两条同项目宣传合并，并把商业接入判定为“授权未清，不接入”：本次未安装 Skill、下载模型或租用显卡。若以后推进短剧或小说宣传片，先使用原创素材和自行编写的镜头库，或取得适当授权，再独立核验模型、LoRA 与素材权利；技术验收看人物连续性、动作穿模和成片返工，不采信作者自评分。MIT 工具代码仍须遵守其许可条件，且安装前需审查。

【证据】[作者仓库与环境说明](https://github.com/huangserva/h3-fight)；[提示词库许可原文](https://github.com/huangserva/h3-fight/blob/main/%E5%BA%93/LICENSE.md)；[个人源发布帖](https://x.com/servasyy_ai/status/2121945482838880421)。

【可信度/待核验点】仓库内容与许可边界：高。B-provisional 来源的速度、质量提升及“一句话出片”效果：待核实，未独立复现，不作为采纳依据。全部第三方模型与 LoRA 的商用许可、生成视频的具体权利边界：尚未逐项核验。

## 3. Codex 容量错误出现修复信号：可以复测，不等于稳定性已验收

【事实】已核验 Tibo 的第一方帖：其称 Codex 团队“might have actually fixed”长期出现的“model at capacity”错误，措辞仍有保留。本次查询 OpenAI 官方状态页显示系统正常；状态页同时注明这是聚合状态，个人可用性会因套餐、模型与功能不同而变化。两项证据都不能证明昱桥账号已恢复，也不是额度上调或重置公告。

【影响】这直接关系到现有 Codex 工程任务能否继续，而非是否应换工具。如果此前任务确实因容量错误暂停，现在有理由重新验证；没有理由仅凭该帖删除重试与回退机制、提高并发或重配整个环境。

【动作】已完成第一方公告与实时状态页交叉核验，未发起模型调用。建议仅对已有受阻任务，用现有合规额度重跑最小可验收步骤；保留失败记录与可交接检查点，再决定是否恢复长任务。若仍报错，先区分服务容量、个人额度与认证问题，不把所有错误都当成这次修复覆盖的故障。本次未改模型、并发、套餐或回退配置。

【证据】[Tibo 第一方原帖](https://x.com/thsottiaux/status/2122206990101536852)；[OpenAI 官方实时状态页](https://status.openai.com)。

【可信度/待核验点】原帖内容及查询时聚合状态：高；修复范围、持续稳定性和个人账号恢复：待核实。保留原帖的不确定措辞；没有本地成功率或性能实验结果。
